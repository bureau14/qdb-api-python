# REST service setup

This setup targets the Go `qdb_rest` server from `bureau14/qdb-api-rest`.
The public REST tool page describes a different configuration interface.
Use the reference configuration packaged as `qdb/etc/qdb_rest.yaml` and the
downloaded binary's `--help` when checking its contract.

The files follow the cluster setup's split: `config.sh` holds defaults,
`binaries.sh` locates the binary, `utils.sh` owns lifecycle helpers, and
`cleanup.sh` archives logs. `default.rest.cfg` is the
base configuration selected by `CONFIG_REST` and passed directly to the server
through `--config`. Each instance overrides listeners, backend URI, and key-file
paths through command-line flags, following the cluster setup's flow. The base
file can use the server's native YAML syntax. The start and stop entrypoints
source those helpers.

The two instances bind HTTP to loopback. `http://127.0.0.1:40080` targets
`qdb://127.0.0.1:2836`, and `http://127.0.0.1:40081` targets the secure cluster
at `qdb://127.0.0.1:2838`. Secure means QuasarDB key authentication. Each instance
also requires HTTPS and Flight listeners, on 40443/40493 and 40444/40494
respectively, because the server always opens those listeners. HTTPS is not
required for this local connectivity check.

Run the service lifecycle from the repository root with Bash, curl, and jq
available. Startup, smoke verification, and teardown have no Python dependency.

```bash
../qdb-artifacts-buildkite-plugin/.venv/bin/python scripts/cicd/prepare-rest-artifacts.py
# Start clusters only if they are not already running.
QDB_ENCRYPT_TRAFFIC=1 bash scripts/tests/setup/start-services.sh
bash scripts/tests/rest-setup/start-services.sh
bash scripts/tests/rest-setup/smoke.sh
bash scripts/tests/rest-setup/stop-services.sh
```

The separate artifact preparation command uses the sibling plugin's Python
environment, credential chain, and storage settings. `--plugin-dir PATH` selects another checkout of that
plugin. It resolves `LATEST_SUCCESSFUL` with strict `refs/heads/master` matching
for the host's release variant and overlays the C API, server, utilities, and REST
packages into `qdb/` without cleaning it. `qdb/rest-artifacts.json` records the
resolved builds, refs, variants, and archive names. CI uses the same extraction
destination while retaining the pipeline's branch and snapshot dependency rules.
The plugin cleans the common destination once before extracting either project.

`URI_INSECURE` and `URI_SECURE` override backend addresses, with or without the
`qdb://` prefix. `USER_PRIVATE_KEY` and `CLUSTER_PUBLIC_KEY` select the files
generated by the cluster setup. The secure REST instance uses both paths for
its readiness connection. The smoke script submits the user file's `username`
and `secret_key` to `/api/v2/auth/login`, then sends `SELECT 1` to `/api/v2/query`
with the returned bearer token. The anonymous instance also requires a login.
Queries request JSON and must return the value 1. They create no database data.
Credential and token files are private temporary inputs and are removed on exit.

`QDB_ENCRYPT_TRAFFIC` is consumed by the cluster setup independently of key
authentication. The REST client keeps its default cipher setting: the current
C API negotiates full-stream encryption with the cluster. Mapping that variable
to REST's `cluster.encryption: aes` fails with the bundled C API because that
cipher is deprecated. Both secure login and queries work with server traffic
encryption enabled and the default REST client setting.

`REST_PORT_INSECURE` and `REST_PORT_SECURE` override the HTTP ports.
`REST_HTTPS_PORT_INSECURE`, `REST_HTTPS_PORT_SECURE`,
`REST_FLIGHT_PORT_INSECURE`, and `REST_FLIGHT_PORT_SECURE` override the other
listeners. Port 0 asks the server to allocate a port for HTTPS or Flight.
The HTTP probe needs fixed, distinct, nonzero ports. Inherited `QDB_REST_*`
server variables are cleared during startup so the base configuration and
explicit instance flags determine which backend each listener serves.

`LOG_DIR_REST` defaults to `.rest/log/`, with static console logs for each
instance and readiness probe logs. Startup stops existing REST instances,
archives previous logs, and clears the log directory
before launching both instances directly in the background. Teardown targets
the exact REST executable name with `pkill` on Unix or `Taskkill` on Windows,
following the cluster setup's process-wide cleanup pattern.

Teardown archives the log directory as
`scripts/tests/rest-setup/logs/rest-logs-<epoch>.tar.gz`.
`REST_LOG_ARCHIVE_PATH` overrides the archive directory. Configuration and
credential files remain outside the log directory. `CONSOLE_LOG_REST_INSECURE`,
`CONSOLE_ERR_LOG_REST_INSECURE`, `CONSOLE_LOG_REST_SECURE`, and
`CONSOLE_ERR_LOG_REST_SECURE` override the console log paths.
`REST_START_TIMEOUT` and `REST_REQUEST_TIMEOUT` default to 60 and 3 seconds.
A startup request can
consume up to two HTTP request timeouts beyond the startup polling deadline.

Startup calls the shared query helper directly for readiness. `smoke.sh` is a
standalone wrapper around the same helper. Login credentials and tokens live
only in the probe's private temporary directory and are removed on exit.

The command list in `.buildkite/steps/_build.yml` starts REST after the clusters.
Startup invokes the query checks before returning. `.buildkite/hooks/pre-exit`
stops REST before stopping the clusters, including after a failing command or
job cancellation. It retains the hook's existing exit status behavior, so
cleanup does not replace the test result. This lifecycle is independent of
`20.test.sh` replacing itself with pytest. After a failed local startup, run
teardown explicitly, as with the cluster setup. The Linux image installs curl
and jq; other agent platforms require both on their PATH. Runtime validation
is performed on Linux amd64. Windows amd64,
Linux aarch64, and macOS aarch64 require validation on their agents.
